# 智能体执行循环设计（Agent Harness）

> 适用版本：`src/2-MVP项目` · 阶段 2（智能体化）
> 代码：`agent/harness.py`（循环）、`agent/store.py`（轨迹日志）、`agent/scenarios.py`（离线回放）
> 一句话：**模型负责「想做什么」，框架负责「能不能做、做了记下来」。**

---

## 一、框架选型：为什么自己写 Harness

先明确一个概念：**Harness 不是某个具体的包**，而是「模型外面的那层脚手架」——
循环控制、工具分发、状态持久化、轮次预算、写操作门禁。LangGraph、OpenAI Agents SDK
都提供了自己的 Harness 实现，也都可以用；本项目的取舍如下：

| 方案 | 能解决什么 | 在本场景的问题 |
|---|---|---|
| **LangGraph** | 图编排 + checkpoint，`interrupt()` 天然支持人工确认 | 引入 StateGraph / Node / Reducer 一套 DSL，业务方读代码门槛高；打断恢复绑在自己的 checkpointer 上，与现有 SQLite 会话体系要再对接一层 |
| **OpenAI Agents SDK** | 轻量、内置 handoff / guardrail | 面向多智能体交接，本场景只有一个智能体；且强绑定 OpenAI 协议风格，换国产模型时要多一层适配 |
| **AutoGen / CrewAI** | 多角色协作、群聊 | 角色扮演范式与「门店补货」这种强流程、强门禁的业务不匹配，反而增加不可控性 |
| **自研 Harness（选用）** | 单智能体 + 固定轮次 + 写操作确认 | 约 300 行，全部可读；日志、门禁、中断在一处闭环，排查不需要跨框架 |

**判断依据**：本场景的循环是**有界、单线程、强门禁**的——最多 5 轮、每次一轮一个模型调用、
写操作必须人工确认。这种结构用显式 `for` 循环表达最清楚；上编排框架属于「用航母送快递」。

> 借鉴而非照搬：中断恢复的「checkpoint + resume」思路来自 LangGraph，
> 但落在自己的 `agent_runs.messages` 快照上，与既有会话/权限体系天然一致。

## 二、执行循环

### 2.1 主循环

```
                    ┌──────────────────────────────┐
                    │  messages = system + 历史 + 问题 │
                    └───────────────┬──────────────┘
                                    ▼
                        ┌───────────────────────┐
                        │ 第 N 轮（N ≤ 5）       │
                        │ ① llm.chat_with_tools │  ← 记录决策日志（耗时/决定调哪些工具）
                        └───────────┬───────────┘
                    无 tool_calls   │   有 tool_calls
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
      ┌───────────────┐                       ┌────────────────────────┐
      │ 最终回答 → 结束 │                       │ ② 逐个执行工具          │
      └───────────────┘                       │   · write 级 → 中断     │
                                              │   · 其它   → 直接执行   │
                                              └───────────┬────────────┘
                                                          ▼
                                              ┌────────────────────────┐
                                              │ ③ 结果写回 role=tool    │
                                              │   记录工具日志           │
                                              └───────────┬────────────┘
                                                          └──→ 回到 ①
```

代码位置：`Harness._loop()`。三个约束写死在代码里，不依赖模型自觉：

1. **轮次上限 5**：`range(start_round, self.max_rounds + 1)`，耗尽后强制收尾，
   不会出现「模型无限自我纠错」把 token 烧光。
2. **一轮可并行多个只读工具**：模型一次返回多个 `tool_calls` 时按顺序执行、逐个回填。
   这是 5 轮能跑完完整补货链路的前提（提示词里明确要求合并查询）。
3. **写操作先中断**：命中 `tools.HITL_TOOLS`（目前只有 `create_replenishment_draft`）时，
   在执行**之前**返回 `confirm_required` 事件并结束本轮流。

### 2.2 轮次预算怎么花（实测）

| 场景 | 轮次 | 说明 |
|---|---|---|
| 制度问答 | 2 轮 | 1 轮检索 + 1 轮回答 |
| 完整补货申请 | **5 轮（用满）** | 见第五节 b |
| 配送可行性 | 2 轮 | 1 轮查询 + 1 轮结论 |

补货链路正好卡在 5 轮：模型只要多浪费一轮（比如先问一句「您是要补哪个商品」），
就会触发轮次耗尽。这是刻意的——**宁可让模型学会批量查询，也不要给它无限预算**。

### 2.3 事件协议

`Harness` 产出 `(event, payload)` 元组，服务层原样转成 SSE：

| 事件 | 时机 | 前端动作 |
|---|---|---|
| `status` | 每轮开始 | 顶部状态条「第 2/5 轮：正在核对…」 |
| `tool` | 工具 running / done | 执行轨迹逐行点亮（✓ / ! / ✕） |
| `confirm_required` | 写操作被挂起 | 渲染**执行前确认卡** |
| `draft` | 草稿真正写入后 | 渲染草稿卡片（第二次确认：提交） |
| `delta` | 最终回答逐片 | 打字机效果 |
| `sources` | 流结束 | 引用来源卡片 |
| `done` | 流结束 | 回填 session_id / run_id / status |
| `error` | 异常 | 中文错误提示 |

## 三、轨迹日志：三张表

| 表 | 一行是什么 | 关键字段 |
|---|---|---|
| `agent_runs` | 一次问答 | `status`（running / waiting_confirm / done / cancelled / failed / rounds_exhausted）、`round_used`、`messages`（中断快照）、`pending_action_id` |
| `agent_steps` | 一次决策或一次工具调用 | `round_no`、`step_no`、`tool`、`args`、`decision`、`duration_ms`、`result_summary`、`ok`、`blocking`、`code` |
| `agent_actions` | 一张待确认卡 | `tool`、`args`、`preview`、`status`（pending / confirmed / cancelled / expired） |

为什么不用 `messages.tool_trace` 那个 JSON 字段就够了？
- 轨迹分析要按轮次/工具/耗时**聚合排序**，JSON 字段没法建索引；
- 人工确认发生在 `/chat` 流结束后的另一个请求里，必须落库才能跨请求恢复；
- 一次问答被中断拆成两段，需要 `run_id` 作为稳定关联键。

### 3.1 一行日志长什么样

```
round_no=5  step_no=1  tool=create_replenishment_draft
decision=interrupt     duration_ms=8
result_summary=已暂停：补货申请预览已推送店长，等待人工确认
```

模型决策单独占 `step_no=0`，`tool=__model__`：
```
round_no=5  step_no=0  tool=__model__  decision=plan  duration_ms=1240
result_summary=第 5 轮：决定调用 1 个工具（create_replenishment_draft）
```

### 3.2 轨迹质量指标

`store.trace_quality(run_id)` 输出，管理后台「执行轨迹」页直接展示：

| 指标 | 含义 | 异常信号 |
|---|---|---|
| `rounds` | 决策轮次数 | 经常 5/5 → 提示词没有让模型批量查询 |
| `tool_calls` | 真实工具调用次数 | 单次 >10 → 可能在绕路 |
| `repeats` | 同工具 + 同参数的重复调用 | >0 → 模型在原地打转（门禁拒绝后重试） |
| `blocked` | 命中业务停止条件次数 | 多 → 数据质量问题（账实不符/零销量/促销） |
| `step_failures` | 工具执行失败次数 | 多 → 参数理解偏差（传商品名不传编码） |
| `round_efficiency` | 工具调用 / 轮次 | <1.5 → 没有合并并行调用 |

## 四、写操作的中断确认

### 4.1 时序

```
浏览器                    服务端                       数据库
  │  POST /chat              │                            │
  │─────────────────────────>│  run + steps…              │
  │  status / tool …         │                            │
  │<─────────────────────────│                            │
  │                          │  模型要建草稿               │
  │                          │  → 干跑 preview（不写库）    │
  │                          │  → agent_actions(pending)  │
  │  confirm_required(预览)  │  → agent_runs(waiting)     │
  │<─────────────────────────│  流结束                    │
  │                          │                            │
  │  （店长看卡片：SKU / 数量 / 整箱换算 / 预计配送日）      │
  │                          │                            │
  │  POST /api/agent/confirm │                            │
  │─────────────────────────>│  校验权限/状态/一次性        │
  │                          │  → 执行 create_draft       │
  │  draft + delta + done    │  → run=done                │
  │<─────────────────────────│                            │
```

### 4.2 为什么必须「执行前」中断

- **执行后确认 = 已经写进去了**。补货草稿一旦落库，即使后来撤回，也已经在表里留下了记录，
  下游（总部审批、仓库分配）可能已经读到。
- 所以框架在调用写工具前先做一次**干跑**（`tools.preview_replenishment_draft`）：
  同样的入参、同样的四项校验，只读地算出「将要写入什么」；
  预览不通过就直接当普通工具失败回填给模型（模型会调整数量重试），不会弹卡。

### 4.3 为什么用「断流 + 恢复」而不是「挂着等」

| 方案 | 问题 |
|---|---|
| SSE 里 `sleep` 等用户点确认 | 网关/浏览器通常 60s 断连；用户关页面就永远挂着；线程被占用 |
| 前端轮询状态 | 需要额外状态机，且回答无法续流 |
| **断流 + 落库 + 新请求恢复（选用）** | 每次请求都很短；刷新页面仍能确认（`GET /api/agent/pending`）；可审计 |

恢复时用 `agent_runs.messages` 快照重建消息链，把店长的决策作为 `role=tool` 的结果回填，
然后**只收尾、不再进入下一轮**——写操作是链路终点，让模型继续决策只会带来重复建单风险。

### 4.4 两道确认不是重复

| | 第一次：执行前确认 | 第二次：提交确认 |
|---|---|---|
| 问题 | 要不要**生成**这张补货草稿 | 要不要**提交**进入总部审批 |
| 触发 | `create_replenishment_draft` 之前 | `POST /api/drafts/{id}/submit` |
| 谁做 | 店长 | 店长 |
| 模型权限 | 只能申请，不能代替 | 完全无权 |

这样设计对应现实流程：先在系统里"起个单"（可改可撤），确认无误后再提交。

## 五、三条典型轨迹（预期 + 实测）

回放命令：`python -m agent.scenarios`（工具/门禁/日志全部走真实代码，只把模型换成脚本）。

### a.「整箱规格和最小起订量是多少」——只查制度，不碰校验和建单

| 轮 | 决策 | 工具调用 | 结果 |
|---|---|---|---|
| 1 | 决定调 1 个工具 | `search_policy_docs(query="整箱规格 最小起订量 MOQ", top_k=3)` | 命中 3 条条款（MOQ / 整箱规格 / 换算公式） |
| 2 | 不再调工具 | — | 给出条款要点 + 引用来源 |

**预期断言**：`validate_replenishment`、`create_replenishment_draft` 不得出现。
实测 2 轮、1 次工具调用，通过。

> 关键点：制度类问题走 RAG 就够了，**不要**因为"补货"两个字就去查库存/校验——
> 那会把 2 轮的问题拖成 5 轮还没结论。

### b.「帮我给门店申请补 20 箱牛奶」——完整链路 + 建单前中断

数据：A002 鲜牛奶 1L，12 盒/箱，MOQ 5 盒，分配上限 120 盒，可售 12 盒，日均 5.3 盒；
配送日一/三/五，线路余量 180 件。**20 箱 = 240 盒 > 上限 120 盒**，所以必然有一次调整。

| 轮 | 决策 | 工具调用 | 结果摘要 |
|---|---|---|---|
| 1 | 并行 4 个只读 | `search_sku(牛奶)` | A002 鲜牛奶 1L（12 盒/箱） |
| | | `get_sellable_inventory(A002)` | 系统 12 / 可售 12（账实一致） |
| | | `check_promotion_status(A002)` | 不在促销窗口，历史销量可用 |
| | | `get_sales_context(A002, 7)` | 近 7 天 37 盒，日均 5.3 |
| 2 | 并行 2 个 | `get_replenishment_policy(A002)` | MOQ 5、整箱 12、上限 120 |
| | | `get_delivery_schedule(2026-11-06)` | 周五可发，线路余量 180 |
| 3 | 换算后送校验 | `validate_replenishment(A002, 240, 11-06)` | **被拒**：超上限 120（建议 10 箱 = 120 盒）；且 240 > 线路余量 180 |
| 4 | 按建议调整 | `validate_replenishment(A002, 120, 11-06)` | 四项通过，签发令牌（15min，一次性） |
| 5 | 申请建单 | `create_replenishment_draft(A002, 120, 11-06, token)` | **⏸ 中断**：预览已推送店长 |
| — | 店长点「确认」 | （框架直接执行，不再问模型） | 草稿 #n 写入，状态 `draft` |

中断卡内容（店长看到的）：

```
商品：A002 鲜牛奶 1L（12 盒/箱）
数量：120 盒（10 箱）        整箱换算：10 箱 × 12 盒/箱 = 120 盒
配送：2026-11-06（周五），东区 1 号线，余量 180 件
✓ 最小起订量：申请 120 盒 ≥ 起订量 5 盒
✓ 整箱规格：120 ÷ 12 盒/箱 = 10 箱
✓ 分配上限：申请 120 盒 ≤ 上限 120 盒
✓ 配送日历：2026-11-06（周五）在配送日历内
✓ 线路容量：申请 120 盒 ≤ 线路余量 180 件
↻ 已按制度调整：原申请 240 件（20 箱）→ 120 件（10 箱）
```

**实测**：5/5 轮、9 次工具调用、1 次阻断、0 次重复调用、轮内效率 2.0。

> 两个值得注意的设计点：
> 1. 超上限时 `validate_replenishment` 直接返回「最多可申请 120 盒（10 箱）」，
>    模型不需要自己试数——**能用确定性计算解决的事，不要交给模型猜**。
> 2. 店长说「20 箱」，最终草稿是 10 箱。这个差异必须在确认卡上明说（`adjust` 字段），
>    否则就是"擅自改客户需求"。

### c.「这批 30 箱牛奶今天能发吗」——查日历与容量，只给结论

| 轮 | 决策 | 工具调用 | 结果 |
|---|---|---|---|
| 1 | 并行 2 个 | `search_sku(牛奶)` | A002，12 盒/箱 → 30 箱 = 360 盒 |
| | | `get_delivery_schedule(2026-11-05)` | 今天周四不在日历，最近可发 2026-11-06 |
| 2 | 不再调工具 | — | 结论：今天不能发；最近 11-06；线路余量 180 < 360，需拆两批 |

**预期断言**：不出现 `validate_replenishment` / `create_replenishment_draft`。
问的是"能不能发"，不是"帮我申请"，**不能顺手建单**。

## 七、接真实模型后必须知道的三件事

离线回放用脚本模型（按剧本调用），**测不出小参数模型的真实行为**。接上 GLM-4-Flash 实测后暴露了三个问题，都已修，但这三条决定了后续换模型时该复测什么。

### 1. 模型一轮只发一个 tool_call → 5 轮预算不够

首次实测「帮我给门店申请补 20 箱牛奶」的结果是 `rounds_exhausted`：5 轮里只查完商品、制度参数、库存、建议量、促销，**校验和建单一次都没跑到**。提示词里「同一轮并行发起多个只读工具」这条指令，小模型不执行。

修法是结构性的，不是加提示词：新增聚合工具 `get_sku_context`，一次返回五项只读上下文，把 5 轮压成 1 轮。修后同一句话 **4 轮完成**（search_sku → get_sku_context → validate → create 前中断）。

> 教训：**当模型做不到某条指令时，应该改结构而不是加重语气。** 把「必须并行」变成「不需要并行」。

### 2. 模型会用系统建议量覆盖客户明确要求

同一轮实测里，店长说「补 20 箱」，模型却调了 `suggest_quantity`（提示词明令禁止），拿到建议量 12 盒，草稿变成**1 箱**。店长若没逐字核对就点确认，等于订错货。

修法有两层，都在框架/工具层，不依赖模型自觉：

| 层 | 做法 |
|---|---|
| 上下文前置 | `get_sku_context` 直接返回「店长指定 20 箱 = 240 盒，超上限 120，最多 10 箱」 |
| 硬门禁 | 框架用正则从原话抽数量存进 `ctx["requested_qty"]`；`suggest_quantity` 见到它就拒绝（`QTY_SPECIFIED`），不给模型覆盖的机会 |

数量意图是确定性的字符串事实，正则比模型可靠。中文数字（「三箱」「十五箱」）一并支持。

### 3. 收尾文案会把落库数量说错

建单后由模型写总结，它从对话历史里捡回「20 箱」，而实际落库是 10 箱——**回答与数据不一致**。

修法：提示里逐条给定事实并明令「数量只能写成 120 盒（10 箱）」，生成后**校验输出是否含正确数字，不含就丢弃模型措辞改用模板**。建单信息不允许由模型自由发挥。

同时确认卡与草稿都带 `adjust` 字段：

```json
{"from_qty": 240, "from_boxes": 20, "to_qty": 120, "to_boxes": 10,
 "reason": "店长原要求 20 箱（240 盒），受起订量/整箱/分配上限/线路容量约束，调整为 120 盒"}
```

落库时 `qty_requested=240`（店长原话）、`qty_suggested=120`（实际申请），两者不同即说明被制度参数压过。

## 七、已知边界

1. **会话状态在进程内存**（`tools._SESSIONS` 里的步骤标记与校验令牌）。
   服务重启或多实例部署时，中断后的确认会因令牌丢失而失败（返回 `TOKEN_INVALID`）。
   → 正式版把 `steps` / `tokens` 落 Redis，key 用 `session_id`。

2. **客户端中途断开可能漏写 message**：`_pump` 的落库在生成器末尾，
   断连时可能被跳过。→ 正式版放 `finally`，并用 `agent_runs.status=running` 做补偿清理。
3. **`agent_actions` 没有过期清理**：卡片可以无限期挂着。
   → 加定时任务把 `pending` 超过 24h 的置为 `expired`。
4. **轮次预算是固定的 5**：不同复杂度场景没有区分。
   → 可按意图分类给 3~8 轮，`agent_runs.max_rounds` 字段已经预留。
5. **离线回放的"模型"是脚本**，只能验证流程与门禁，验证不了模型的自然语言质量。
   → 换模型/改提示词后，仍需用真实模型跑一轮，对比 `agent_steps` 的工具序列与轮次。

## 八、停止条件转交（v2 新增，对应访谈 f44 / f25）

### 8.1 问题

改造前命中停止条件只做了一半：`blocking=True` 让模型停下并说明原因，
但「谁接手、什么时候前处理完」没有落点。f44 要求的是三件套：
**原因 + 接手人 + 人工确认时间**；f25 还要求「不能只把状态改成已转交」。

### 8.2 做法

```
工具返回 blocking=True
  → harness 调 agent/incidents.py 按错误码取归属规则
  → store.create_incident 落 agent_incidents（同一 run + 同一错误码只留一条 pending）
  → SSE tool 事件附带 incident 字段
  → 前端在工具轨迹行下方显示「已转交 补货计划员 唐映秋，11-06 18:31 前处理」
  → 管理后台 /admin/audit 可查同一张单并点「已处理」（写 handled_at / handled_by）
```

归属不编造，直接取访谈报告六位受访者的岗位：账实不一致 → 补货计划员（f15）；
编码未归并 → 数据工程师（f30）；促销版本 → 门店店长（f13）；
制度未命中 → 知识库管理员。时限按风险分级：促销/现场确认 8h，常规 24h，编码治理 48h。

### 8.3 为什么不用「模型说一句请找计划员」

模型措辞无法统计、无法超时提醒、无法证明谁接了。
落表后可以直接算：待处理数、超时数、平均闭环时长——这才是可以拿去验收的东西。

## 九、另外三项配套改动（v2）

| 改动 | 原状态 | 现在 |
|---|---|---|
| 编码未归并 | 一律 `blocking`，试点 SKU 会被大面积卡死 | 先查 `sku_code_map`，命中即按主编号继续；未命中才阻断并转交数据工程师 |
| 未满足数量 | `basis.unsatisfied = qty − 线路余量`，校验通过后恒为 0 | 改为「店长原要求 − 实际申请」，确认卡与草稿卡显示「少给了多少、因为上限」 |
| 留存与归档 | 日志只增不减 | `retention.py`：90 天到期先导出 `archive/*.jsonl`，再删除；补货单与未处理转交单不删 |

`RETENTION_DAYS` 可在 `.env` 中调整；执行接口需 `confirm=ARCHIVE`，且只能由管理员在页面二次确认触发。
