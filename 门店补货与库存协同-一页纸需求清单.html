门店补货与库存协同系统 · 一页纸需求清单

需求评审版 V1.0 · 2026-10-30
评审人：架构师 × 项目发起人
项目定位：独立部署的补货协同决策系统（不嵌入 ERP）。服务「总部 — 总仓 — 10 家门店」的内部协同闭环：基于 T+1 销售与库存数据，按可配置规则自动生成补货建议，经人工确认后执行，并以经营看板度量效果。

二、核心业务闭环

T+1 数据同步（ERP/POS）→ 数据对账校验→ 规则计算（安全库存 / min-max / 阈值）→ 补货建议单→ 店长确认 / 调整（留痕）→ 执行 / 采购单导出→ 回单核销→ 每日指标看板

三、十项关键决策记录

#决策结论架构影响
Q1独立系统，不嵌 ERP自建商品/库存/门店/供应商主数据模型与 RBAC + 行级权限；工期较外挂模式 +30%~40%
Q2T+1 批量同步（文件/接口）轻量 ETL + 每日对账告警，不引入消息队列/实时管道；看板注明数据日期
Q3系统建议 + 人工确认建议单状态机（生成→确认→执行→核销），人工调整全程留痕，超时 24h 微信提醒
Q4一期固定规则引擎参数化规则可按商品类目自助配置；规则改前可用历史数据试算；计算层独立封装，为二期 ML 预测预留替换点
Q510 店 / 千级 SKU单体应用 + MySQL/PG 单库，2C4G 云主机起步；表结构按 100 店量级留余量
Q6店长移动优先推荐微信小程序（免安装、订阅消息触达）+ PC Web 双端共用一套 API
Q7区域只读催办；告警广播+认领；±50% 超限审批缺货告警三级同时可见、谁处理谁认领；全系统仅保留一级审批
Q8供应商不进系统无对外 API 暴露面；采购需求走导出/邮件；单据模型预留对外扩展
Q9每日快照看板（非实时）轻量指标层（批处理后刷新），4 项核心指标口径评审期冻结签字
Q106 个月内上线一期砍至核心闭环；里程碑见第五节

四、一期范围边界

✓ 一期做（In Scope）

  • 主数据管理（四类主数据 + 初始导入清洗）
  • T+1 数据同步 + 自动对账告警
  • 规则引擎 + 参数配置 + 规则历史试算
  • 补货建议单全生命周期 + 超限审批 + 留痕
  • 微信小程序端（店长）+ PC Web 端（总部）
  • 缺货告警广播与认领
  • 每日经营看板（4 指标，三视角下钻）
  • 采购要货单导出（Excel）

✗ 一期不做（Out of Scope）

  • 需求预测 / ML 算法（二期，仅预留接口）
  • 自动生成单据并直接下发执行
  • 供应商 VMI、到货预约、EDI 对接
  • 实时数据管道（CDC / 消息队列）
  • 原生 App（iOS / Android）
  • 店间调拨（待确认，若需要补入数据模型）

六、主要风险

  1. 主数据质量：商品条码 / 门店档案初始清洗是最大人力黑洞，实施计划须预留专项清理期
  2. 指标口径之争：缺货率分母、周转销量窗口等口径须在开发前由运营总监签字冻结，否则看板验收必延期
  3. 店长确认不及时：建议单堆积将使闭环空转，靠小程序订阅消息 + 超时升级提醒兜底，试点期人工督导
  4. ERP 导出稳定性：T+1 依赖上游文件格式，上游改版需建立变更通知机制

七、待确认事项

  • 现有 ERP / 收银系统产品及导出方式（决定主数据同步为标准接口还是定制开发）
  • 是否允许店间调拨（影响数据模型，M1 前必须定）
  • 预算区间与交付方式（自研 / 外包 / 混合）
  • 4 项看板指标计算口径的正式确认与签字
