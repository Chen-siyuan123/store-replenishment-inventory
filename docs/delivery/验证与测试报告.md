# 门店补货与库存协同智能体 · 验证与测试报告

> 回答一个问题：**这套系统"行为正确"有什么证据？**
> 本文汇总项目全部可复现的验证手段：单元测试、离线评测、离线轨迹回归，以及它们与 30 条评测用例、上线检查清单的对应关系。所有离线验证**不调用大模型 API**，任何人 clone 仓库后两条命令即可复现。

---

## 一、验证体系总览

| 层级 | 手段 | 覆盖什么 | 依赖模型？ | 位置 |
|---|---|---|---|---|
| L1 单元测试 | pytest，25 个断言组 | 框架层纯函数、安全分区、销量口径、提交契约 | 否 | `tests/test_framework_basics.py` |
| L2 离线评测 | `eval/run_eval.py` 一键产出报告 | 用例资产完整性、检索门禁、轨迹回归 | 否 | `eval/`（报告：`eval/eval_report.md`） |
| L3 端到端评测 | 30 条用例按 `expected_behavior` 人工评 | 真实模型下的回答质量与工具序列 | 是 | `eval/cases_v1.json`（试点期执行） |
| L4 上线检查 | 25 项清单（6 项阻塞） | 工程上线 readiness | — | `docs/delivery/上线前检查清单.html` |

## 二、L1 单元测试：框架层防线

测的对象全部是**必须 100% 可靠、放在框架层而不是提示词里**的确定性逻辑：

**数量抽取防线**（`extract_requested_qty` / 中文数字解析，9 个用例）
- 背景：实测模型会拿系统建议量覆盖店长的明确要求（20 箱 → 1 箱事故）。所以「店长明确说了多少」由正则解析，模型改不动。
- 覆盖：阿拉伯数字、中文数字（十五 / 二十 / 二十三 / 两）、多单位（箱/盒/瓶/袋/包）、无数量、零数量、多数量取第一处。

**工具风险分区**（`TOOL_RISK` / `HITL_TOOLS` / `TOOLS_SPEC` 三表一致性，4 个用例）
- 断言 1：整个系统**写操作只有 `create_replenishment_draft` 一个**——任何新增写工具混进登记表都会让测试失败；
- 断言 2：强制中断集合（HITL）严格等于写集合——写必中断，不写不中断；
- 断言 3：11 个工具的规格表与风险表一一对应——防止某个新工具漏登记风险级别就被调用。

**销量口径**（`sales_window` / `avg_daily_from_rows`，6 个用例）
- 窗口只取「已经结束的自然日」：今天还没过完，销量不完整，进窗口会拉低日均；
- 日均的分母是**有销售记录的天数**，不是自然日天数：断货日 / 漏同步日若按 0 摊进分母，日均被低估 → 建议量偏低 → 补了还是不够，而系统不报错；
- 回归护栏：一旦退回 `total / days` 口径，用例立即失败。

**提交契约**（`approval_check`，6 个用例）
- 系统没有审批路由、没有 `approver` 字段、`allocated` / `rejected` 状态无写入点，所以只能判定「要不要线下确认」，不能返回「已批准」；
- ±50% 阈值含边界不触发，超出才提示；
- 静态守护：源码里不允许再出现「等待总部确认与仓库分配」这类做不到的承诺。

运行方式：

```bash
python -m pytest tests/ -v      # 需要 pytest
python tests/test_framework_basics.py   # 无 pytest 环境的直接运行兜底
```

## 三、L2 离线评测：一键复现

```bash
python eval/run_eval.py        # 全量：资产盘点 + 检索预检 + 三条轨迹
python eval/run_eval.py --fast # 只跑前两项
```

最新一次结果（完整报告见 `eval/eval_report.md`，每次运行自动重新生成）：

### ① 用例资产盘点

30 条评测用例（制度类 10、工具调用类 10、绕约束意图类 5、多轮上下文类 5），**全部用例的期望工具均真实存在于工具注册表**，无悬空引用——用例本身也是被验证的对象。

### ② 制度类检索预检（模型"不编制度"的第一道门禁）

10 条制度题跑真实混合检索（与 `search_policy_docs` 工具同一套实现）：

| 检查项 | 结果 |
|---|---|
| 正常题 top1 命中正确章节 | **7 / 7** |
| 陷阱题（制度中无答案）正确判空 | **3 / 3** |

陷阱题即「门店退货和报损流程」这类制度里没写的问题——早期版本会硬编一段回答，现在的相关性门禁会返回空、让模型答「制度中未找到」。

### ③ 三条离线轨迹回归（换模型 / 改提示词后的基准）

用 ScriptedLLM 按轮次回放决策，**工具层、门禁、中断确认、日志全部走真实代码**，轨迹真实写入数据库、可在管理后台回放：

| 场景 | 内容 | 轮次/上限 | 写操作中断 | 结论 |
|---|---|---|---|---|
| a | 制度问答（只走 RAG） | 2 / 2 | — | ✅ 通过 |
| b | 补货申请（完整链路：查库存销量 → 算量 → 门禁校验 → 中断确认 → 落库） | 5 / 5 | 触发 | ✅ 通过 |
| c | 配送可行性（只查日历，不建单） | 2 / 2 | — | ✅ 通过 |

回归断言包括：最终状态、轮次上限、必需工具出现、禁止工具不出现、写操作中断被触发。这三条脚本就是「预期轨迹」——以后换模型、改提示词、改工具，重跑一遍对比是否跑偏。

### ④ 可核对的运行实录

断言只能说明「过没过」，看不出过程。为此把场景 b 的整条轨迹从 `chat.db` 的三张轨迹表原样导出成
[`运行实录-20箱牛奶案例.md`](运行实录-20箱牛奶案例.md)（导出脚本 `scripts/export_run_trace.py`，不含人工改写）：

| 轮次 | 动作 | 结果 |
|---|---|---|
| 1 | 调 4 个工具：查商品 / 可售库存 / 促销状态 / 近 7 天销量 | 可售 12 盒、日均 5.3 盒、非促销期 |
| 2 | 查制度参数与配送日历 | MOQ 5 盒、12 盒/箱、上限 120 盒、线路余量 180 件 |
| 3 | 按店长要求 20 箱（240 盒）校验 | **阻塞**：超分配上限 120 盒、超线路余量 180 件，`VALIDATION_FAILED` |
| 4 | 改为 120 盒重校验 | 四项全过，签发 15 分钟一次性令牌 |
| 5 | 建草稿 → 中断等确认 | 草稿 #28 落库，`store01` 确认后进入待提交 |

实录里能看到模型收到的每个工具返回、预检五项逐项打勾、以及「原 240 → 实际 120」的调整原因——这是「系统真的拦住了不该建的 20 箱」最直接的证据。

### ⑤ 30 条用例的覆盖矩阵（哪些自动判、哪些必须人评）

「30 条用例」容易被误读成「30 条都跑过了」。实际的判定能力是分层的，逐项列出：

| 判定项 | 涉及用例 | 判定方式 | 当前结论 |
|---|---|---|---|
| 期望工具是否真实存在 | 30 / 30 | 离线：读 `TOOLS_SPEC` 比对 | ✅ 0 处悬空引用 |
| 制度检索是否命中正确章节 | 10 / 10（制度类） | 离线：`probe_retrieval` 阈值回归 | ✅ 正常题 7/7 命中、陷阱题 3/3 判空 |
| 工具选择是否正确（该调 / 不该调） | 20（工具链 10 + 绕约束 5 + 多轮 5） | 需真实模型执行后比对轨迹 | ⏳ 未执行，试点期人评 |
| 回答是否引用正确条款、不编造 | 30 / 30 | 需真实模型 + 人工评审 | ⏳ 未执行 |
| 越权 / 绕约束意图是否被拦住 | 5 | 端到端需模型；门禁本身有单测兜底 | ⚠️ 门禁有单测，端到端未跑 |

结论一句话：**可离线判定的部分（工具资产、检索门禁）100% 通过；需要模型参与的部分（20 条工具选择、30 条回答质量）尚未执行**，安排在六周试点期按 `expected_behavior` 逐条人评。这张表就是「别把资产盘点说成端到端验证」的边界。

工具层耗时另有一份可复现基线：[`性能基线.md`](性能基线.md)（235 次真实调用，p50 5 ms / p95 14 ms）。

## 四、CI：每次推送自动复验

`.github/workflows/ci.yml` 在每次 push / PR 时自动执行三步检查并上传评测报告为 artifact：

1. **语法检查**：`python -m compileall -q prototype eval tests scripts`（不依赖第三方 lint 工具，任何环境都能跑）
2. **L1 单元测试**：`python -m pytest tests/ -v`
3. **L2 离线评测**：`python eval/run_eval.py`

整个流程离线可跑，不依赖任何 API 密钥。同一分支连续推送时，`concurrency` 会取消上一轮，避免排队。

## 五、诚实的边界：还没验证什么

- **端到端回答质量**（L3）需要真实模型参与，30 条用例已备好评分口径，安排在六周试点期逐条人工评审——现在只能证明「流程跑通、门禁生效」，不能证明「降了缺货率」。
- **上线检查清单 25 项中自评 6 项阻塞**（无限流、令牌在进程内存、无降级开关等），未通过前不上线，处置方案见检查清单文档。清单 v1.1 已按代码复核修正：A2 日志留存策略实际已实现（`retention.py`，先归档后删除、草稿与待办不清理），从阻塞项移出，剩余偏差是各表未按 90/180 分级保留。
- 跨店数据隔离目前只做了应用层（会话绑定 + 越权 403 + store_id 过滤），数据库行级安全策略未上，列入试点前整改。
