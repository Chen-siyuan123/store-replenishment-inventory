## 与代码的对应关系

**需求假设 → 实现落点**（每条 REQ 都能在代码里找到对应，可逐条核对）：

| 报告需求 | 实现位置 | 状态 |
|---|---|---|
| REQ-1 可售库存与缺货标识口径 | `tools.py` 四类停止条件 + `sku_code_map` 旧码映射（`db.py`） | 防御已做，口径治理未做 |
| REQ-2 整箱 / 起订量 / 线路容量内嵌 | `tools.py` `validate_replenishment` 四项校验 + 拒签令牌 | 已实现 |
| REQ-3 促销版本结构化随建议流转 | `tools.py` 促销版本确认 + 样本不足 3 天阻断 | 部分（促销日历未结构化）|
| REQ-4 预计到货与未满足数量 | `tools.py` `basis.shortfall` + 确认卡展示 | 部分（无分段延迟归因）|
| REQ-5 停止条件 + 人工复核 + 留痕 | `agent/incidents.py` 转交单 + `agent/store.py` 三表 + 建单前 HITL 中断 | 已实现 |
| REQ-6 缺货率 / 周转 / 报废三指标 | 未实现（建议试点后用 SQL 出周报） | 未做 |

**其他对应**：

- 架构设计里的「执行循环」对应 `src/2-MVP项目/agent/harness.py`
- 「工具层与门禁」对应 `src/2-MVP项目/tools.py`
- 「知识库检索」对应 `src/2-MVP项目/kb.py`、`kbstore.py`
- 「日志留存」对应 `src/2-MVP项目/retention.py`（90 天先归档再删除）
- 上线检查清单中的每一项，都在该清单里标注了真实状态（已具备 / 需补 / 阻塞）
