# 拾光连锁 · 门店补货与库存协同 AI 需求分析方案

> 版本：v1.0（2026-11-06）
> 用途：把「痛点 → AI 改造 → 优先级 → 需求边界与规格 → 追溯矩阵 → 验收标准」串成一条可核对的链路。每个编号都能回溯到原始材料。
> 依据材料：`拾光连锁-业务需求发现报告.md`（36 条事实 retail-f00~f55、REQ-1~REQ-6）、`门店补货与库存协同-现状流程图.html`（痛点红框）、`门店补货与库存协同-一页纸需求清单.html`（范围收敛）、`拾光连锁-试点验收方案.md`（验收口径）、`docs/README.md`（REQ → 代码对应表）、`验证与测试报告.md`、`性能基线.md`。
> **注意**：所有需求均为待验证假设；带「待签字」的口径须经业务方书面确认后才生效。

---

## 一、分析方法与流程

本方案沿用需求发现报告的三个框架（frameworks/workflow-decomposition、outcome-risk-matrix、4-source-convergence），按以下五步展开：

```
第 1 步  现状流程拆解      → 四泳道（店长/计划员/仓库/财务），定位每个判断点的数据失真
第 2 步  痛点归因          → 痛点编号 P-01~P-09，逐条挂 f 编号（本方案第二节）
第 3 步  AI 改造识别       → 每个痛点映射可做的 AI 改造项 A-01~A-10，区分「AI 能做/规则能做/暂不做」（第三节）
第 4 步  优先级排序        → 价值 × 风险可拦截性 × 可行性评分，输出 P0/P1/P2 与三阶段路线图（第四节）
第 5 步  规格化与验收定义  → 范围边界 → 需求规格 FR/NFR → 追溯矩阵 → 分层验收清单（第五~九节）
```

关键原则（来自需求发现报告）：
1. **先治理口径，再谈预测**——最值得先做的不是销量预测模型，而是「可售库存与缺货标识」前置环节（f10/f12/f31/f30）。
2. **高风险优先于高效率**——停止条件与人工复核是不可逆风险点，优先级高于效率收益（f44/f15）。
3. **切入点按流程分段定位，不整体上 AI**——约 30% 延迟补货源于配送排队而非预测（f51）。
4. **覆盖率不代表验收通过**——验收只认三指标 + 库存约束（f02/f42/f53）。

## 二、痛点清单（现状归因）

来源：现状流程图痛点红框 + 需求发现报告按角色整理的证据。

| 编号 | 痛点 | 现象描述 | 依据 | 业务后果 |
|---|---|---|---|---|
| P-01 | 可售库存口径失真 | 货在后仓但货架空，系统仍算有库存，消费者看到空货架 | f10 | 缺货率 12% 的分子分母不可靠 |
| P-02 | 账实差异高 | 每天盘点 20 个重点 SKU，账实差异平均约 8% | f12 | 建议量建立在错误库存上 |
| P-03 | 销量样本失真 | 销量为零可能是缺货截断，不一定没人买 | f31 | 按零销量推算会漏补爆款 |
| P-04 | 编码混乱 | POS/WMS 中新旧码、套装码并存 | f30 | 主编号对不齐，口径无法统一 |
| P-05 | 约束靠人工记忆 | 最小起订量、整箱规格、仓库分配上限、线路容量、周一三五配送日全凭店长经验 | f20、f50 | 建议量脱离约束，计划员无法采用，试点退化为人工重算 |
| P-06 | 促销信息不结构化 | 促销变价使预测失效；促销日历运营维护但门店改价不总回传；临时促销靠群聊/个人表补充 | f11、f21、f14 | 促销期误差无法单列，建议按旧口径推 |
| P-07 | 延迟无归因 | 约 30% 延迟补货是配送排队而非预测问题；门店看不到分配依据、预计到货与未满足数量 | f51、f01、f52 | 把排队问题算到预测头上，AI 投入打偏，门店不信任 |
| P-08 | 异常交接不留痕 | 异常靠群聊补说明再回系统补录；转交只改状态不写处理人/时限/原因 | f14、f25、f44 | 责任说不清，「只说了不能办、没人接手」 |
| P-09 | 验收口径未固定 | 三指标的分母、统计周期、排除规则待业务负责人签字 | f53、f00、f42 | 试点结论效力打折，指标可被「多备货」操纵 |

## 三、AI 改造清单（痛点 → 可做的改造）

| 编号 | AI 改造项 | 改造内容与技术手段 | 解决的痛点 | 可行性判断 | 现状 |
|---|---|---|---|---|---|
| A-01 | 制度知识库智能问答 | BM25(jieba)+FAISS 混合检索、两级相关性门禁：相关度不达标直接回答「制度中未找到」，禁止编造条款 | P-05（制度/约束透明化） | 高：制度文档已结构化入库 | ● 已实现 |
| A-02 | 自然语言补货建议 | LLM（GLM）+ 自研执行循环（最多 5 轮）：模型决策 → 工具执行 → 结果回填；每条建议携带依据（库存/销量/制度条款/促销版本） | P-05、P-07、P-08 | 高：链路已通，4 轮完成建单 | ● 已实现 |
| A-03 | 约束内嵌校验引擎 | **确定性规则而非模型**：MOQ / 整箱 / 分配上限 / 配送日四项校验，通过才签发一次性令牌；令牌改任一字段即失效；数量由框架层正则独立提取，提示词注入无法绕过 | P-05 | 高：20 箱牛奶案例已被实际拦截 | ● 已实现 |
| A-04 | 写操作人工确认（HITL） | 模型无任何直接写库权限；建单执行前强制中断，店长确认后才落库 | 风险兜底（P-08 关联） | 高 | ● 已实现 |
| A-05 | 停止条件自动转交 | 六类业务停止条件（账实不一致、零销量、新旧码未归并、促销版本未确认、依据缺失、系统不可用）返回 blocking=true，模型必须停下；自动开转交单：原因 + 接手岗位 + 处理时限，后台可查待办/超时/闭环 | P-08 | 高 | ● 已实现 |
| A-06 | 数据质量防御阻塞 | 零销量判空、账实不一致阻塞、旧码映射（sku_code_map）、缺关键字段进人工修复队列不用猜测值补齐 | P-01、P-02、P-03、P-04 | **拦截已做；口径治理（缺货标识以哪个系统为准）未做**——需秦芮出字段清单、顾明岚裁定 | ◐ 部分实现 |
| A-07 | 促销版本结构化流转 | 促销版本作为结构化字段随建议落库；未带版本建单触发 `PROMO_VERSION_REQUIRED` | P-06 | 机制已做；促销日历本身未结构化（运营侧数据缺口） | ◐ 部分实现 |
| A-08 | 延迟归因分段分析 | 取配送单据流水，按「截单 → 配送 → 签收」分段统计延迟归因，区分配送排队 vs 预测误差 | P-07 | 中：依赖配送单据流水取数（单量与耗时样本尚未核实） | ○ 试点后规划 |
| A-09 | 多指标周报自动出数 | 缺货率/周转/报废三指标 + 促销期误差单列，按周出数，分母与排除规则按签字口径 | P-09 | 中：建议先以 SQL 周报落地，指标口径签字后实施 | ○ 未实现（REQ-6） |
| A-10 | 销量预测模型 | 时序预测 / 促销感知预测 | —— | **暂缓**：口径未治理前建模输入被污染（f10/f12/f31/f30），且 30% 延迟与预测无关（f51）。待 A-06 口径治理完成 + 试点三指标出数后再评估 | ⏸ 明确暂缓 |

**AI 改造的边界判断**（对应「能不能做」的三分法）：
- **AI 能做的**：自然语言理解与问答（A-01/A-02）、依据组织与展示（A-02）、异常转交的文本生成（A-05）。
- **必须由规则做的**：约束校验（A-03）、写操作门禁（A-04）、数据阻塞（A-06）——凡不可逆动作前的校验一律用确定性规则，不信任模型置信度。
- **暂不做的**：自动下单（供应商接口未审批，f32）、不改供应商合同（f52）、短保与冷链（f40 另组）、顾客个人数据进模型（f41 红线）。

## 五、需求边界

### 5.1 范围内（In Scope）

- 试点范围：8 家门店、50 个常温 SKU、6 周、**并行试点**（不关闭现有人工报数流程，f02/f05）。
- 系统产物：**补货申请草稿**——先出草稿、店长人工确认、再提交；提交后由总部确认与仓库分配。
- 交互方式：店长自然语言提问，智能体基于门店库存、销量、补货制度与配送日历给出有依据的建议。
- 数据接入：历史销售与库存 CSV 导出（f32，供应商下单接口未审批）；试点数据每天两次刷新、原文按版本同步（f34）。
- 知识库：补货制度文档检索问答（BM25+FAISS 混合检索 + 门禁）。
- 审计：执行轨迹三表落库、管理后台可查、日志 90 天先归档再删除（f43/f45）。

### 5.2 范围外（Out of Scope）——明确不做

| 不做 | 原因 | 依据 |
|---|---|---|
| 自动下单 / 自动采购 | 不能直接上线；下单接口未走完审批 | f22、f32 |
| 审批与仓库分配 | 系统只出草稿，审批权在总部与仓库 | 一页纸需求清单 |
| 修改供应商合同 | 不在权限与范围之内 | f52 |
| 短保与冷链商品 | 与常温分开设组，报废/缺货账不能混 | f40 |
| 顾客个人交易数据进模型 | 只用聚合的商品与门店数据 | f41 |
| 直接覆盖人工流程 | 并行试点，未经确认的结果不覆盖原记录 | f05、f15 |
| 销量预测建模（首期） | 口径未治理前输入被污染；30% 延迟与预测无关 | f10/f12/f31/f30、f51 |
| 既有系统采购节省额核算 | 不纳入节省额 | f03 |

## 六、需求规格

### 6.1 功能需求（FR）

> 每条规格含：描述 / 输入 / 处理 / 输出 / 约束与异常 / 优先级 / 来源。

**FR-01 可售库存口径与编码归并**（P0，REQ-1）
- 描述：补货建议前必须把库存换算为「可售口径」，并按主编号归并新旧码与套装码。
- 处理：旧码经 `sku_code_map` 映射归并；账实不一致且店长未确认 → 阻塞；缺关键字段进人工修复队列，不用猜测值补齐（f33）。
- 异常：销量为零/无记录（疑缺货截断）→ 阻塞，不得据此推算建议量（f31）。
- 遗留：缺货标识以 POS/WMS/门店盘点哪个系统为准 **待裁定**（未定事项 1）。

**FR-02 约束内嵌校验与一次性令牌**（P0，REQ-2）
- 描述：建议量必须通过 MOQ / 整箱 / 分配上限 / 配送日四项校验。
- 处理：`validate_replenishment` 校验通过才签发一次性令牌；`create_replenishment_draft` 校验令牌内容与申请一致；数量由框架层正则独立提取（防提示词注入）。
- 异常：任一项不通过 → 拒签令牌并说明原因；令牌改任一字段即失效。

**FR-03 停止条件与人工复核**（P0，REQ-5）
- 描述：六类触发条件（临时促销、缺货截断、账实不一致、依据缺失、系统不可用、新旧码未归并）出现时停止自动建议。
- 输出：转交单三要素——原因 + 接手人/岗位 + 处理时限（f44、f25）；管理后台可查待办、超时与闭环。
- 约束：未经确认的结果不能覆盖原记录（f15）；模型无直接写库权限，建单前 HITL 中断。

**FR-04 建议依据可追溯**（P0，REQ-5）
- 描述：每条建议携带依据整条存 JSON（`basis`）：库存、销量、制度条款版本、促销版本、预计到货与未满足数量（f52）。
- 约束：审核日志保留各数据版本、建议内容、人工修正与签核人，能重建当次处理；不记录口令与非必要个人信息（f45）。

**FR-05 制度知识库检索门禁**（P0，REQ-2 支撑）
- 描述：BM25+FAISS 混合检索，两级相关性门禁；相关度不达标回答「制度中未找到」，禁止编造条款。
- 异常：制度未覆盖的问题不得用模型知识硬答。

**FR-06 促销版本结构化流转**（P1，REQ-3）
- 描述：促销版本作为结构化字段随建议落库流转；未带版本建单触发 `PROMO_VERSION_REQUIRED` 阻断。
- 遗留：促销日历本身未结构化（运营侧）；字段最小集需试填一周。

**FR-07 预计到货与未满足数量展示**（P1，REQ-4）
- 描述：确认卡向门店展示预计到货与本次未满足数量（basis.shortfall）。
- 遗留：无分段延迟归因；到货时间发布责任人 **待定**（未定事项 6）。

**FR-08 轨迹留痕与审计**（P0，REQ-5）
- 描述：每轮决策、每次工具调用（参数/耗时/结果摘要）、每次中断确认落轨迹三表（agent_runs / agent_steps / agent_actions）；`/admin/trace` 可查，可导出实录。

**FR-09 日志留存与归档**（P1，f43/f45）
- 描述：日志按保留期（试点 90 天）到期先导出 `archive/*.jsonl` 再删除；补货申请单与未处理转交单不清理。
- 约束：90 天是试点口径，不是正式留存期限。

**FR-10 多指标周报**（P2，REQ-6）
- 描述：缺货率 / 周转 / 报废三指标 + 促销期误差单列，按周出数；分母、周期、排除规则按签字口径执行（f53）。
- 状态：未实现，建议试点期先以 SQL 周报落地。

### 6.2 非功能需求（NFR）

| 编号 | 需求 | 指标/口径 | 依据 |
|---|---|---|---|
| NFR-01 | 性能 | 工具层 p95 ≤ 15ms（实测 235 次调用 p50/p95/max = 5/14/58ms）；模型推理延迟不计入工具层基线 | 性能基线.md |
| NFR-02 | 数据边界 | 顾客个人交易记录不进入任何计算，只用聚合数据 | f41 |
| NFR-03 | 权限与安全 | 模型无写库权限；JWT 登录态；PBKDF2 密码哈希；密钥不进仓库 | 架构设计 |
| NFR-04 | 可用性降级 | 接口失败时继续原人工流程，保留只读快照与时间戳；恢复后按业务编号去重补齐，不重复创建待办 | f35 |
| NFR-05 | 数据新鲜度 | 试点数据每天两次刷新；超过一个周期的结果标注待刷新，历史快照不伪装成当前状态 | f34 |

> 分五层：L1 单元 → L2 离线评测 → L3 过程性验收 → L4 业务结果 → G 上线门禁与终止条件。全部离线验证不调用大模型 API，clone 后可复现。
