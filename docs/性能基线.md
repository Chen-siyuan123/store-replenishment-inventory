# 性能基线

回答「这套系统快不快、慢在哪」。数据来自 `chat.db` 的 `agent_steps` 表——每次工具调用都记录了
`duration_ms`（工具函数自身执行耗时），样本为本地已完成的三条离线轨迹与历史运行。

> 采集口径：`python scripts/latency_stats.py`（表格由脚本生成，`--write` 可回填本文件）。
> 不含模型推理时间，也不含网络。离线回放（ScriptedLLM）下模型侧耗时为 0，因此本表只反映**工具层**。

## 二、怎么读这张表

- **工具层不是瓶颈**：p50 5 ms、p95 14 ms、最慢一次 58 ms（配送日历查询，含线路容量汇总）。用户感知的等待几乎全在模型侧，优化工具 SQL 没有意义。
- **两条写操作链路耗时接近**：`validate_replenishment`（6/11 ms）与 `create_replenishment_draft`（7/22 ms）都在十毫秒级，说明「校验令牌 → 建单」这道防线**不会让人等**，这是它敢放在主链路上的前提。
- **制度检索 15 次均为 0 ms**：走的是进程内缓存路径（`kb.py` 的检索缓存）；冷启动首次检索不在样本内，含分词建索引与向量计算，明显慢于 0 ms。
- **最慢的两次都在配送日历**：因为它要连算「线路剩余容量 + 下一个可发日 + 当日是否在日历内」，是唯一带多表聚合的只读工具。

## 三、三段延迟要分开说

| 环节 | 量级 | 依据 |
|---|---|---|
| 工具层（本表） | 5~14 ms | 235 次真实调用 |
| 检索（冷启动首次） | 数十~数百 ms | 含 jieba 分词与向量化；命中缓存后 <1 ms |
| 模型推理 | 秒级 | 供应商侧，未纳入本表；SSE 流式输出首字可见 |

答辩时如果被问「系统响应多快」，正确答法是**分段回答**：「工具层毫秒级，慢的是模型；所以界面用 SSE 边生成边显示，用户不会盯着白屏等。」

## 四、这份基线不能证明什么

- **没有并发压测**：样本来自单人本地运行，多店并发下的 SQLite 锁竞争未测。
- **没有真实模型时延**：离线回放模型侧为 0，真实首字延迟取决于供应商与网络。
- **不含前端渲染**：只覆盖后端工具层。
- 因此它只能作为「改工具后有没有变慢」的对比基线，不能当 SLA 承诺。

## 五、复现

```bash
cd src/web && python -m agent.scenarios    # 产生样本（写库）
python scripts/latency_stats.py                  # 打印当前统计
python scripts/latency_stats.py --write          # 回填本文件的数据段
```
