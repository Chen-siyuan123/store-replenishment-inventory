## 二、部署架构

```
用户浏览器
    │  HTTPS
    ▼
WorkBuddy 托管网关（app.workbuddy.host，注入 sharecode 鉴权，转发至容器）
    │  HTTP → 127.0.0.1:$PORT
    ▼
容器内：python serve.py（读取 PORT）→ uvicorn server:app
    │
    ├─ 静态页面：index.html（对话式补货界面）
    ├─ /api/*   ：登录(JWT) / 对话(SSE 流式) / 草稿 / 转交 / 知识库
    └─ SQLite   ：SKU、库存、促销、销量、补货草稿、转交单、审计日志
```

**启动链路**：托管环境注入 `PORT` 环境变量 → `serve.py` 读取后以 `uvicorn` 拉起 `server:app` → `db.py` 检测到空库自动建表并灌入种子数据 → 服务就绪。

## 三、部署过程中的关键适配（真实问题与解决方案）

### 3.1 端口适配

托管平台通过 `PORT` 环境变量告知监听端口，原 `run_local.bat` 固定端口不可用。新增 `src/2-MVP项目/serve.py` 启动器：

```python
port = int(os.environ.get("PORT", "8000"))
uvicorn.run("server:app", host="0.0.0.0", port=port)
```

本地验证：`PORT=8765 python serve.py` 后 `curl http://127.0.0.1:8765/` 返回 HTTP 200。

### 3.2 反向代理剥离/覆盖 Authorization 头（本次部署最关键的适配）

**现象**：本地一切正常的 `Authorization: Bearer <JWT>` 鉴权，在托管地址上全部返回 401。

**定位过程**：新增 `/api/health` 诊断端点，回显服务端实际收到的凭证通道：

```json
{ "ok": true, "build": "2026-11-06-auth-fallback",
  "token_header": true, "token_query": false, "token_cookie": false }
```

发现网关会**注入自己的 Authorization 头**（覆盖应用的 JWT），自定义 Cookie 也被过滤。

**解决方案**：`src/2-MVP项目/auth.py` 的 `get_current_user` 改为**多通道依次验签**——按 `Authorization → X-Access-Token → Cookie → query 参数 token` 顺序尝试，取第一个验签通过的凭据；通道无效（如代理注入的假头）自动跳到下一条。前端 `index.html` 的 `apiFetch` 同步携带 `X-Access-Token` 头与 query token 兜底。

**验证结果**（线上实测）：Bearer / X-Access-Token / query token 三条通道均 200，无凭证 401，行为与本地完全一致。

### 3.3 登录态 Cookie 下发

`/api/login` 在返回 JWT 的同时下发 `HttpOnly + Secure + SameSite=Lax` 的 `access_token` Cookie，浏览器同源访问不依赖任何自定义头。
